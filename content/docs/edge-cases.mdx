title: Edge Cases
description: Handle tricky navigation scenarios — direct link clicks, hard reloads, back/forward, unsupported browsers, and more.

The View Transitions API is powerful, but real apps have edge cases: users clicking links directly, hitting refresh, pressing back, navigating before a transition finishes, or running browsers that don't support `startViewTransition` yet. This guide covers the common ones and shows how to handle them gracefully.

## Direct Link Navigation

When a user clicks a link, the browser handles the navigation itself — you don't get a chance to call `document.startViewTransition`. To animate link-driven navigations, intercept the click, prevent the default behavior, and push the new URL inside the transition callback.

Here's a reusable `TransitionLink` for Next.js App Router that wraps `router.push` in a view transition:

```tsx title="components/transition-link.tsx"
"use client";

import Link, { LinkProps } from "next/link";
import { useRouter } from "next/navigation";
import {
  AnchorHTMLAttributes,
  ReactNode,
  useEffect,
  useRef,
  useTransition,
} from "react";

interface TransitionLinkProps
  extends LinkProps,
    Omit<AnchorHTMLAttributes<HTMLAnchorElement>, keyof LinkProps> {
  children: ReactNode;
}

export function TransitionLink({
  children,
  href,
  ...props
}: TransitionLinkProps) {
  const router = useRouter();
  const [isPending, startTransition] = useTransition();
  const resolveRef = useRef<(() => void) | null>(null);

  // Fires once the router.push-driven update has committed.
  useEffect(() => {
    if (!isPending && resolveRef.current) {
      resolveRef.current();
      resolveRef.current = null;
    }
  }, [isPending]);

  const handleClick = (e: React.MouseEvent<HTMLAnchorElement>) => {
    e.preventDefault();

    if (!document.startViewTransition) {
      router.push(href.toString());
      return;
    }

    document.startViewTransition(() => {
      return new Promise<void>((resolve) => {
        resolveRef.current = resolve;
        startTransition(() => {
          router.push(href.toString());
        });
      });
    });
  };

  return (
    <Link href={href} onClick={handleClick} {...props}>
      {children}
    </Link>
  );
}
```

The transition stays open until the new route has actually rendered. `useTransition` + `isPending` lets you resolve the transition promise only after React commits the new page, so the animation covers the whole swap instead of firing too early.

The same pattern works with TanStack Router:

```tsx title="components/TransitionLink.tsx"
import { Link, useNavigate, type LinkProps } from "@tanstack/react-router";
import { useCallback, useEffect, useRef } from "react";

export function TransitionLink({
  href,
  children,
  ...props
}: LinkProps & { href: string; children: React.ReactNode }) {
  const navigate = useNavigate();
  const resolveRef = useRef<(() => void) | null>(null);

  useEffect(() => {
    // Resolve the transition after the router commit by listening to the
    // route mount. Simplify with a deferred callback in your app.
    const resolve = resolveRef.current;
    if (resolve) {
      resolveRef.current = null;
      resolve();
    }
  });

  const handleClick = useCallback(
    (e: React.MouseEvent<HTMLAnchorElement>) => {
      if (e.metaKey || e.ctrlKey || e.shiftKey || e.altKey || e.button !== 0) {
        return; // let the browser handle modified clicks
      }
      e.preventDefault();

      if (!document.startViewTransition) {
        navigate({ to: href });
        return;
      }

      document.startViewTransition(() => {
        return new Promise<void>((resolve) => {
          resolveRef.current = resolve;
          navigate({ to: href });
        });
      });
    },
    [href, navigate],
  );

  return (
    <Link to={href} onClick={handleClick} {...props}>
      {children}
    </Link>
  );
}
```

### Only intercept same-origin navigations

Never run a view transition for external links, hash anchors, or downloads. Check the target before intercepting:

```tsx
const handleClick = (e) => {
  const anchor = e.currentTarget as HTMLAnchorElement;
  const isSameOrigin = anchor.origin === window.location.origin;
  const isHash = anchor.getAttribute("href")?.startsWith("#");
  const isDownload = anchor.download !== undefined;

  if (!isSameOrigin || isHash || isDownload) return;
  e.preventDefault();
  // ...wrap navigation in startViewTransition
};
```

## Hard Reloads and Deep Links

When a user types a URL, hits refresh, or lands on the page from another site, there is no outgoing view to animate. That's fine — and expected. Don't try to force an animation for the initial load; browsers can't snapshot a page that doesn't exist yet.

What you *can* do is animate the **incoming** snapshot. Target `::view-transition-new(root)` on the first render. The old snapshot will be blank, so keep the `new` animation dominant:

```css
::view-transition-new(root) {
  animation: fade-in 400ms ease both;
}
```

Make sure the `old` snapshot doesn't leave a visible blank frame:

```css
::view-transition-old(root) {
  animation: none;
}
```

## Back and Forward Navigation

The browser keeps a navigation history entry. When users press back/forward, the popstate navigation swaps the DOM. If you only wrap `router.push` in a transition, back/forward clicks will swap without animation.

Handle it centrally in your router adapter. In Next.js, listen to the `popstate` event and wrap the resulting state update:

```tsx
"use client";

import { useEffect, useRef } from "react";

export function useViewTransitionOnPop() {
  const resolveRef = useRef<(() => void) | null>(null);

  useEffect(() => {
    const onPop = () => {
      if (!document.startViewTransition) return;
      // Prevent the default back/forward swap so we can animate it.
      // In practice, pair this with your router's navigation handler.
    };
    window.addEventListener("popstate", onPop);
    return () => window.removeEventListener("popstate", onPop);
  }, []);
}
```

> **Tip:** For frameworks with a router plugin (like Astro's View Transitions or the experimental Next.js View Transition router), back/forward is handled for you — prefer those when available.

## Unsupported Browsers

Firefox and Safari shipped `startViewTransition` in 2024–2025, but older versions and some webviews still lack it. Always feature-detect and fall back to an instant (or plain CSS) change:

```ts
function navigateWithTransition(navigate: () => void) {
  if (!document.startViewTransition) {
    navigate();
    return;
  }
  document.startViewTransition(navigate);
}
```

Your transition **CSS** should also degrade. The `::view-transition-*` pseudo-elements are ignored by unsupported browsers, so the worst case is the page swaps instantly with no animation — no broken layout, no stuck overlay. Just make sure you don't depend on JavaScript listeners inside keyframes that would leave state half-applied.

## Respecting prefers-reduced-motion

Many users prefer reduced motion. The View Transitions API doesn't honor the media query automatically, so gate your animations:

```css
@media (prefers-reduced-motion: reduce) {
  ::view-transition-old(root),
  ::view-transition-new(root) {
    animation: none !important;
  }
}
```

And in JavaScript, skip the transition wrapper entirely:

```ts
const prefersReducedMotion =
  window.matchMedia("(prefers-reduced-motion: reduce)").matches;

if (prefersReducedMotion || !document.startViewTransition) {
  navigate();
} else {
  document.startViewTransition(navigate);
}
```

## Rapid, Overlapping Clicks

Users can click links faster than a transition completes. `startViewTransition` skips an already-running transition and snapshots mid-flight, which can cause visual stutter. Debounce or ignore new navigations while one is pending:

```ts
let pending = false;

async function navigateWithTransition(navigate: () => void) {
  if (pending) return;
  if (!document.startViewTransition) {
    navigate();
    return;
  }

  pending = true;
  const transition = document.startViewTransition(navigate);
  try {
    await transition.finished;
  } finally {
    pending = false;
  }
}
```

## Async Data Before the Swap

If your page loads data (auth checks, fetch, server round-trip) before rendering, the transition promise must wait for it — otherwise the animation completes while the new page is still a loading skeleton.

```ts
const transition = document.startViewTransition(async () => {
  await loadPageData(); // resolve after data is ready
  updateDOM();
});
```

For frameworks like Next.js App Router, combine `startViewTransition` with `useTransition` (as in the `TransitionLink` example) so the promise resolves after the committed render, not after the navigation *starts*.

## Same-URL and Anchor Navigations

Navigating to the current URL (a link to the page you're on) triggers no DOM swap. Guard against it, or you'll animate an identical page:

```ts
if (href === window.location.pathname + window.location.search) return;
```

Hash changes (`#section`) update scroll position but not the document. Don't wrap them in a transition — let the browser scroll natively.

## What Not to Animate

- **The very first paint** — nothing to animate from; keep it instant.
- **External sites** — you don't own the next document.
- **Downloads / `target="_blank"`** — new browsing contexts, no snapshot.
- **Iframes** — the same-origin requirement usually blocks snapshotting cross-origin iframes.

## Checklist

- [ ] Feature-detect `document.startViewTransition` before every use
- [ ] Honor `prefers-reduced-motion` in CSS and JS
- [ ] Intercept same-origin link clicks only (skip hash, external, modified clicks)
- [ ] Wrap back/forward navigation too, not just `push`
- [ ] Guard against rapid, overlapping transitions
- [ ] Resolve the transition promise after async data / commit, not before
- [ ] Skip animations for the initial load, same-URL, and anchor navigations
- [ ] Keep `::view-transition-old(root)` empty on direct-entry pages
